## 2026-08-24 14:07 - Block a push on a missing or dishonest §6.7 test-suite declaration, with suite detection and an init-time ask step

**Reasoning:** SPEC 2.0 §6.7's declaration matrix has 3 of 6 rows BLOCK (missing declaration, or 'none' contradicted by a detected suite) and #276 shipped only the allow-and-report half, deliberately, to avoid wedging existing installs before a setup flow existed to collect the declaration. This PR builds that setup flow (clud-bug init detects a package.json test script and asks, per 'Setup MUST ask, and MUST NOT complete without an answer') and the detector the block path needs to tell 'none' from a lie ('Detection is what makes none honest'), so the block can ship safely.

**Alternatives considered:** Block unconditionally on any missing declaration, no detection at all — rejected: cannot distinguish an honest 'none' from a lie, and the SPEC's own reason for detection ('Detection is what makes none honest') would be unmet., Keep allow-and-warn forever and never revisit — rejected: SPEC 2.0 §6.7 is explicit that 3 of 6 rows in the table BLOCK; leaving all of them as allow-and-warn is not a partial implementation of the gate, it is a different (advisory-only) gate that never matches the table., Detect via a full per-ecosystem test-runner integration (pytest, cargo test, go test invocations) instead of filename/package.json heuristics — rejected as disproportionate: the block verdict for the 'nothing declared' rows does not depend on detection at all (only the wording does), so a lightweight heuristic is sufficient and the one row where detection DOES gate the verdict ('none') only needs to catch obvious contradictions, not certify absence.

**Implications:**
- Every repo with an already-installed push-trigger pre-push hook and no 'tests' key in .clud-bug.json will BLOCK on its next push once it runs 'clud-bug update' after this ships — clud-bug's own repo was exactly this case; fixed here by adding 'tests': 'npm test' to this repo's own .claude/skills/.clud-bug.json in the same PR.
- The bootstrap exemption (a push touching only .clud-bug.json is always allowed) is load-bearing: without it, the block itself would be unfixable by a normal PR once merged, since the pre-push hook reads the declaration from the base ref, not the branch being pushed.
- clud-bug update cannot prompt (runs unattended in the self-update Action) — it now returns 'advisories' the CLI prints as warnings instead, so an already-installed repo that never re-runs init is warned, not silently left to discover the block by having a push rejected.

## 2026-08-24 15:33 - CI-only failure root cause: init --commit never checked git commit exit status, and the e2e test fixture had no repo-local git identity

**Reasoning:** Two integration tests failed on CI only after #321 merged with dev. All 3 of the coordinators ordered hypotheses (my own nodeerror branch firing under a stripped CI PATH; a dash/sh bashism in the new hook lines; the dev merge #320 touching hooks.ts output) were checked against the actual CI log and ruled out: the printed output was the PRE-EXISTING "no default-branch ref for remote origin" fail-open message from #276, byte-identical to the annotation already present in the ORIGINAL pre-fix CI run for this same PR, so it predates every panel fix. Root cause: init-tests-declaration.test.js makeRepoDir() never set a git identity (unlike the makeRepo() helper every sibling test file already uses), and runInit() redirects HOME to an empty temp dir for the spawned CLI, so git commit inside main.ts --commit had no identity source except gits OS-level username+hostname auto-detect fallback -- which succeeds with a warning on macOS but fails hard on a fresh Ubuntu Actions runner. main.ts spawned git add/git commit via spawnSync without ever checking .status, so the CLI reported success while the origin fixture repo was left with zero commits; the two e2e tests then cloned that empty repo and got "cloned an empty repository" instead of a resolvable default branch.

**Alternatives considered:** Patch the hook script itself (the coordinators primary hypothesis) -- rejected once the CI log showed the printed message was the untouched pre-#321 no-baseref branch, not any of the three new #321 messages; there was nothing in hooks.ts to fix., Only fix the test fixture (add git config to makeRepoDir) and leave main.ts as-is -- rejected: that patches the symptom in this one file but leaves the same silent-success footgun live for any real user whose machine (or a future CI image) lacks a usable git identity; the class of bug is "spawnSync exit status ignored," not "this test happened to hit it.", Force GIT_AUTHOR_*/GIT_COMMITTER_* env vars in runInit instead of repo-local git config -- rejected: env vars would ride along through the {...process.env, HOME: dir} spread and could mask the exact HOME-isolation gap being fixed; repo-local config is read before any env/global/system/auto-detect fallback, so it is the more direct fix and matches the convention already used in hooks.test.js and pre-push-hook.test.js.

**Implications:**
- Reproduced end to end: cloning a zero-commit origin locally reproduces the identical "no default-branch ref" + "warning: You appear to have cloned an empty repository" signature seen on CI; a commit using only repo-local config still succeeds with every other identity source (HOME, GIT_CONFIG_GLOBAL/SYSTEM, GIT_AUTHOR/COMMITTER env) stripped, proving the fix does not depend on host auto-detect behavior either way.
- Could not reproduce the exact CI-side failure locally (no Linux sandbox available; macOS git auto-detects an identity from username+hostname even with every config source stripped) -- confirmed empirically by reverting the makeRepoDir fix and rerunning: all 9 tests still pass locally, which is expected given the mechanism, not a sign the fix is wrong. This fixs revert-proofing therefore rests on the CI evidence chain (original run annotation + new run log, both byte-identical) rather than a local revert-shows-red demonstration.
- main.ts --commit now warns (never aborts the whole init) on a failed git add or git commit, naming the likely cause; revert-proofed with a new, platform-independent test using a pre-commit hook that always exits 1 (orthogonal to identity/auto-detect variance) -- reverting the exit-status check fails that test (missing "git commit failed" in stderr), restoring passes it again.
- Also closed out hypothesis (b) directly: the pre-push hook script passes `dash -n` and, run for real under /bin/dash (not bash-as-sh) against a broken-node scenario, produces the correct CRITICAL-1 fail-open output -- no bashisms in any of the #321 additions.
