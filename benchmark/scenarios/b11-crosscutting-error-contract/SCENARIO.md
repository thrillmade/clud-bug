severity: MED-HIGH
one_line_defect: normalizeTransfers guards account resolution with try/catch, assuming parseAccountId() throws on a malformed reference, but the helper returns null on failure — so the guard never fires and an unresolved { to: null } transfer slips into `accepted` and is applied to the ledger.
reproduction: node reproduce.mjs
why_no_single_line: Every line of the transfers diff is individually correct — it resolves both endpoints inside a try/catch, accepts the resolved transfer, and diverts failures to `rejected`; the defect is the mismatch between what the diff assumes parseAccountId does (throw on malformed input, so the catch is the rejection gate) and what it actually does (return null, its documented total-function contract), and that contract lives in validate.mjs, a file the diff only exposes, never changes.
correct_finding: Report that normalizeTransfers' "malformed references are rejected" contract is broken because parseAccountId (validate.mjs) signals failure by returning null, not by throwing, so the try/catch guard is dead code — a malformed reference resolves to null, `{ from, to: null }` is pushed to `accepted`, and applyTransfers debits a real account against the null endpoint; ground it either by running `node reproduce.mjs` (the "not-an-account" transfer is never rejected and ACCT-1000 is debited -1400 instead of -500) or by naming the violated invariant (a total function that returns null on failure cannot be error-handled with try/catch — the null must be checked explicitly).
---

The transfers PR (module.mjs) normalizes a batch of transfer instructions and promises that any malformed account reference is rejected before it can move money. It resolves each endpoint with the pre-existing `parseAccountId()` and wraps the resolution in a `try/catch`, treating the catch as the rejection gate. But `parseAccountId()` in validate.mjs is a total function: its contract is to return `null` on a malformed reference, never to throw. So the catch is unreachable — a bad reference resolves to `null`, the transfer `{ from: 1000, to: null, amount: 900 }` is pushed into `accepted`, `rejected` stays empty, and `applyTransfers` debits the real source account against a null destination, silently misrouting money that should have been refused.

Fix: check the resolver's result instead of relying on it to throw — in normalizeTransfers, reject the instruction when `from === null || to === null` (or, alternatively, change parseAccountId in validate.mjs to throw so the existing guard becomes live). The root cause is the assumed-vs-actual error contract of parseAccountId, which lives in validate.mjs — a file the reviewed diff only imports and never changes — which is exactly why a line-quoting reviewer that never opens validate.mjs, and sees a perfectly ordinary try/catch, misses it.
